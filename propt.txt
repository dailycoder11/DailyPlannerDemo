Create a small harness layer between LLM tool requests and actual tool execution. Enforce these 4 rules:

1. **Global tool-call limit**
   - Maximum 3 successfully executed tool calls per user request.
   - Rejected calls do not count.
   - Once the limit is reached, disable further tools and tell the LLM:
     "Maximum tool-call limit reached. No more tools can be used. Produce the best final plan using information already collected and mention anything that could not be verified."

2. **Duplicate-call prevention**
   - Track tool name + normalized arguments.
   - Block an identical tool call that has already been successfully executed.
   - Example:
     `get_travel_time(A,B)` twice → block second.
     `get_travel_time(A,B)` then `get_travel_time(B,C)` → allow.
   - Return the rejection reason to the LLM so it can choose another action.

3. **Weather date guardrail**
   - The original user input contains the trip `start_date` and `end_date`.
   - `get_weather` may only request dates within this range, inclusive:
     `start_date <= requested_weather_date <= end_date`
   - The allowed range must come from the original user input, not from values generated by the LLM.
   - If the LLM requests weather outside this range:
     - block the call before invoking Open-Meteo,
     - do not count it toward the 3-call limit,
     - tell the LLM:
       "Weather can only be requested for dates within the trip start and end dates. Use a valid trip date or continue with the information already available."

4. **Attraction result cap**
   - `search_attractions` may receive many results, but return at most 10 to the LLM.
   - Enforce this in code.
